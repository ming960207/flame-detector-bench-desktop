# 2026-10-12 现场继电器指令可靠性与工序隔离修复

## 现场证据

- 13:30–13:46（北京时间）D:\\exe 打包程序上传的连续四批显示六路继电器 FAIL；桌面日志出现 `DIO_READ_FAILED` 和 `DIO_CONNECTION_FAILED`。现场仍需核实打包程序实际版本、DIO 网络、供电和映射，不得据此判定六件产品全部失效。
- 13:51 与 13:58 从 D:\\上位机界面原型版 源码运行目录上传的日志中，六路故障继电器反馈全部正常；13:58 D3 火警复位延迟、D5 火警无转变、D6 火警初始电平已为 1。
- 六路采用独立 TCP 端口，FF 广播控制帧**无设备 ACK**。本地 socket.write 回调只证明写入传输层，最终“下发到位”只能由真实 DIO 触点按时、稳定地翻转及复位证明。

## 本补丁的实施设计

1. **同端口指令有序：** 原始 TCP 上 A000/A001 的 FF 帧通过已有 `RawTcpModbusClient.sendRawFrame()` 的每连接异步队列；F000=1234 继续使用 01 地址请求并等待标准 Modbus 回包。不会占用其他五路端口，也不改变串口模式兼容行为。
2. **不新增工序：** 保留 FAST_BATCH 六路并行的火警动作、1 秒拍照、复位、故障动作、复位。保持现有动作反馈最长 2 秒、复位默认 3 秒、三次初始幂等广播和原窗口内一次有界补发。持续波形/PLC/打印链路保持原样。
3. **DIO 是唯一正式动作确认：** 本地广播写成功不等于实物动作；需要原始电平连续稳定变化（默认三次、每隔 200ms）。复位需要规定窗口内恢复，超时仍是 FAIL；晚到的紧急清理结果另记，不会冲销既有失败。
4. **安全先决条件：** 如果测试开始时 DIO 读取失败，或任何关联报警/故障触点已经处于配置定义的动作态，本检测位不执行盲发控制；保存 `RELAY_BASELINE_NOT_NORMAL` 或读失败诊断，进入阻断复测，其他工位继续。后续按既有安全复位路径清理，没有自动放行。
5. **闭环追溯：** 对每个动作记录本地写入成功数/尝试数、补发数、物理稳定确认时间、复位时限内确认、紧急清理后的最终恢复情况。结果写入现有按批次自动上传的文件。

## 必须遵守的边界

- 不能把 FF 写入成功当成设备 ACK；不能靠增加无限重发、延长 PLC 流程或放宽 NG 阈值提高“合格率”。
- 初始化失败、触点初始异常、DIO 读取失败均不得放行，需查找设备/治具/接线/版本后再测。
- 生产现场禁止在被测产品未安全复位时继续执行下一阶段。
- 先验证 CI，再在停产维护窗口测试真实六路：常态、单路接触不良、DIO 断连、FF 丢包、F000 复位延迟、异常初始电平、火警灯拍摄、PLC 节拍和打印。
- 核对 D:\\exe 与 D:\\上位机界面原型版 两套运行目录的可执行程序与配置，不可认为仓库更新已自动覆盖现场打包程序。
