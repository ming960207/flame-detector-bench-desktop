# 产品类型、探测器预检与波形有效性改进方案

## 1. 目标

在现有火焰探测器检测台正式流程中增加“产品配置驱动”的检测前置校验，并调整探测器通讯顺序，使设备在检测位 1 夹具/探针下压完成后，先读取并核对产品身份与基础状态，再切换到连续波形发送模式。

本次改进解决以下问题：

1. 首页缺少当前被测产品类型，操作人员无法明确当前批次按哪一类产品标准检测。
2. 软件版本号此前仅能读取，但未纳入正式生产检测判定。
3. 探头数量虽能从 0x1000 读取，但未与产品类型建立对应关系，可能出现三波长产品装入双波长/四波长版本后仍继续检测。
4. TCP 连接建立后原逻辑立即重复发送波形模式切换指令，缺少设备身份/状态预检步骤。
5. 某些无数据探头会表现为“绝对值接近上限、波动量很小”，仅按普通噪声上下限判断容易误认为有效稳定信号。
6. 双波长产品存在少于三路有效探头的正常情况，不能因为未使用通道表现为无数据而误判；必须先以产品类型和设备上报探头数确定本轮应关注的有效探头集合。

---

## 2. 产品类型模型

首页新增“产品类型”下拉框，提供：

- 双波长 `DUAL_WAVELENGTH`
- 三波长 `THREE_WAVELENGTH`
- 四波长 `FOUR_WAVELENGTH`
- 图探型 `IMAGE_DETECTOR`

产品选择属于本批次检测条件。正式流程运行期间锁定，不允许中途切换；流程结束/回到待机后允许重新选择。

系统记住最后一次选择，重启后恢复，减少现场重复设置。

### 2.1 默认探头数量映射

| 产品类型 | 期望探头数 | 说明 |
| --- | ---: | --- |
| 双波长 | 2 | 只关注前 2 路有效探头 |
| 三波长 | 3 | 关注前 3 路 |
| 四波长 | 4 | 关注前 4 路 |
| 图探型 | 3 | 当前按三路光学探头 + 图像能力的产品画像处理；后续如现场协议确认不同，可调整配置模型 |

双/三/四波长的期望探头数由产品类型固定；图探型保留后续扩展空间。

## 3. 产品配置

在“通信与显示配置/设置”界面新增“产品检测配置”区域。

每种产品至少配置：

- 期望软件版本号
- 期望探头数量（双/三/四波长显示固定值；图探型允许后续扩展）

软件版本允许输入常见显示格式，例如：

- `01020304`
- `01.02.03.04`
- `0x01020304`

比较前统一去除分隔符及 `0x`，转换为大写 8 位十六进制字符串进行匹配。

如果某产品未配置期望版本，则状态显示“未配置版本基准”，不应伪造 PASS；正式生产建议配置完整后再投用。

配置继续存储在 `system-config.json`，与现有现场配置一并开箱即用。

## 4. 正式流程通讯顺序调整

### 4.1 原流程

1. 后端启动并连接 6 台探测器 TCP/RTU 通道。
2. TCP 建连成功后立即发送波形发送模式切换指令。
3. 如果没有收到合法波形，持续重试发送模式。
4. PLC 到达检测阶段后直接使用收到的波形数据进行分析。

问题：设备基础身份与状态尚未确认，波形推流已经开始；在持续推流状态下再插入 Modbus 查询也会增加原始 RTU/TCP 字节流解析复杂度。

### 4.2 新流程

正式现场模式下采用“连接传输层，但延迟波形推流”的策略：

1. 软件启动：建立探测器 TCP/RTU 传输连接，但**不立即开启连续波形发送**。
2. PLC 正式流程启动。
3. 到达检测位 1。
4. 垂直电机/夹具下压步骤 `M10.3` 完成（由 `stepM10_3: true -> false` 的阶段转换识别）。
5. 进入 `PRODUCT_PRECHECK` 产品预检。
6. 对每台启用探测器顺序读取：
   - 软件版本 `0x7000/0x7001`
   - 报警/故障状态 `0xA000/0xA001`
   - 探头数量 `0x1000`
7. 将读取结果与首页当前产品类型对应的期望配置比较。
8. 记录每台探测器预检 PASS/NG 和原因。
9. 无论预检是否存在 NG，均继续尝试开启波形（便于保留完整故障证据），但 NG 必须进入最终判定门禁，不能最终判为合格。
10. 预检结束后才发送波形模式切换指令，并沿用现有“ACK + 无合法波形继续重试”的恢复机制。
11. 流程完成后停止/解除本轮波形推流状态，为下一批预检恢复干净的 Modbus 查询阶段。

### 4.3 异常恢复

- 单台探测器预检读取失败：标记 `PRECHECK_READ_FAILED`，继续检查其他设备并尝试后续推流。
- 预检期间通信断开：按现有连接恢复机制重连；该设备本批预检结果保持 NG，除非在波形正式开始前完成一次新的完整预检。
- 软件在流程中途启动：如果 PLC 已经越过检测位 1 下压步骤但本批尚无预检记录，应立即执行恢复性预检，再开启波形。

## 5. 产品预检判定

每台探测器增加预检信息：

- `expectedProductType`
- `expectedSoftwareVersion`
- `actualSoftwareVersion`
- `expectedProbeCount`
- `actualProbeCount`
- `fireAlarm`
- `fault`
- `checkedAt`
- `verdict`: `PASS | FAIL | PENDING`
- `reasons[]`

建议原因码：

- `SOFTWARE_VERSION_NOT_CONFIGURED`
- `SOFTWARE_VERSION_MISMATCH`
- `PROBE_COUNT_MISMATCH`
- `DETECTOR_FAULT_AT_PRECHECK`
- `PRECHECK_READ_FAILED`

报警状态中的 `fireAlarm` 作为检测前状态证据展示和归档；当前不单独因为检测前存在火警状态而新增失败规则，避免改变未确认的生产判定语义。`fault=true` 则直接作为预检失败项。

### 5.1 最终结果门禁

正式最终结果满足原有波形/工序判定的同时，还必须：

- 所有启用探测器完成预检；
- 软件版本与所选产品版本一致；
- 探头数量与产品类型一致；
- 无预检故障状态。

任何一台存在上述异常，本批最终结果至少为 NG，并在对应槽位/探测器卡片明确显示具体原因。

## 6. 波形有效探头规则

### 6.1 根据产品类型确定关注通道

- 双波长：只把 P1、P2 作为本产品要求的有效探头。
- 三波长：P1、P2、P3。
- 四波长：P1、P2、P3、P4。
- 图探型：当前按 P1、P2、P3；后续协议确认后可扩展。

设备实际上报 `probeCount` 与产品期望数量不一致时：

1. 立即记录 `PROBE_COUNT_MISMATCH`；
2. 不允许通过最终判定；
3. 波形界面仍显示实际收到的通道，便于排障；
4. 对所选产品理论上应存在、但实际无有效数据的探头增加“无数据/疑似悬空”标记。

双波长产品未要求的 P3/P4 即便表现为固定高值，也不参与双波长产品 NG 判定。

## 7. “绝对值接近上限 + 波动极小”的无数据判定

新增 `NO_PROBE_DATA` / `PROBE_SIGNAL_STUCK_HIGH` 检测。

单个**应参与本产品检测的探头**同时满足以下特征时，判定为无有效数据：

1. 绝对量非常高，接近配置上限；
2. 波动量/RMS 很低；
3. 在一个最小采样窗口内持续满足，而不是单点瞬态。

第一版建议采用现有质量参数自适应，不额外制造难以维护的绝对常数：

- `absolute >= maxNoiseAbsolute * 0.95`
- `fluctuation <= minNoiseRms`
- 满足现有最小噪声样本数后再判定

该规则目的不是替代普通噪声超限，而是识别“ADC/通道接近饱和值但几乎不变化”的悬空、未接探头或无真实信号情形。

对应原因码：

- `PROBE_SIGNAL_NO_DATA`
- 可附带具体通道，例如 `probe3`。

最终界面应区分：

- 普通噪声过大
- 探头绝对值超限
- 探头疑似无数据/固定高值
- 产品探头数量不匹配

避免全部显示成同一个“噪声超限”。

## 8. 首页 UI

首页标题区域新增“产品类型”选择器，要求：

- 当前产品类型始终可见；
- 待机状态可切换；
- PLC 自动流程运行后锁定；
- 锁定时显示“本批已锁定”；
- 当前产品期望版本号同时显示在选择器旁边，方便操作员确认；
- 本批实际预检完成后显示 `版本 x / 探头数 x` 的汇总状态。

各探测器卡片新增：

- 实际软件版本
- 实际探头数
- 产品预检状态
- 版本不一致/探头数不一致/无数据探头等原因标记

## 9. 设置 UI

现有“通信与显示配置”中新增“产品检测配置”：

| 产品类型 | 期望软件版本 | 期望探头数 |
| --- | --- | ---: |
| 双波长 | 可编辑 | 2 |
| 三波长 | 可编辑 | 3 |
| 四波长 | 可编辑 | 4 |
| 图探型 | 可编辑 | 默认 3 |

保存配置不应触发 PLC 写入；仅更新本机产品检测基准。

## 10. 数据与 MQTT

测试归档、正式结果和 MQTT 检测结果应增加：

- `product_type`
- `expected_software_version`
- 每台 `actual_software_version`
- 每台 `expected_probe_count / actual_probe_count`
- 每台预检 verdict/reasons
- 无数据探头列表

这样云端与本地报告都能追溯“当时选择了什么产品、按哪个软件版本基准检测、设备实际返回什么”。

## 11. 实现顺序

1. 新增产品配置模型和持久化。
2. 新增首页产品类型选择与流程锁定。
3. 新增设置界面软件版本配置。
4. 扩展 FlameDetectorService：现场模式延迟波形推流。
5. 新增正式批次 `PRODUCT_PRECHECK`，读取版本/报警/探头数。
6. 将预检结果加入 Field Summary / WebSocket / UI。
7. 将预检 NG 加入最终判定门禁。
8. 波形分析按产品期望探头集合执行，并增加固定高值无数据判定。
9. 扩展归档与 MQTT 检测结果。
10. 编译、CI、模拟数据和现场 FAT 验证。

---

## 12. 验收场景

至少覆盖：

1. 选择双波长 + 设备返回 2 探头 + 版本一致：预检通过，只评估 P1/P2。
2. 选择三波长 + 设备返回 2 探头：明确 `PROBE_COUNT_MISMATCH`，最终 NG。
3. 选择四波长 + 设备版本错误：明确 `SOFTWARE_VERSION_MISMATCH`，最终 NG。
4. 六台设备中仅一台版本错误：仅该槽位标红，整批 NG。
5. 探头绝对值长期接近上限、波动很小：标记 `PROBE_SIGNAL_NO_DATA`，而不是普通稳定信号。
6. 双波长产品 P3 固定高值：因为 P3 非本产品要求通道，不应因 P3 单独判 NG。
7. 预检期间单台断线：该台 `PRECHECK_READ_FAILED`，其他设备继续，整批 NG。
8. 流程运行后尝试修改产品类型：前后端均拒绝。
9. 流程结束后可重新选择下一批产品。
10. 软件中途启动并发现 PLC 已越过检测位 1：执行恢复性预检后再开启波形。
